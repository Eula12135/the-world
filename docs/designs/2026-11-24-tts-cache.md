# 本地语音缓存（LRU）设计记录

- 日期：2026-11-24
- 状态：已实现
- 相关：`src/services/voice/ttsCache.ts`、`src/services/voice/tts.ts`

## 1. 目标

同一条消息再次点「朗读」时直接本地秒播，不再请求 TTS 接口，省额度、省等待。

## 2. 缓存键

```
hash( 接口地址 · 模型 · 音色 · 服务端语速 · 增益 · 语气指令 · 文本 )
```

用两路不同种子的 FNV-1a 拼成 16 位十六进制，作为 IndexedDB 主键。

**这是整个方案唯一的正确性关键**：键必须"宁多勿少"，漏掉任何一个会改变波形的参数，就会出现"换了音色却播了旧声音"的反向 bug，而且用户完全看不出来。反过来，多带一个不影响波形的参数只是降低命中率，不会出错。

刻意**不**进键的两个字段：

- **音量**：只在播放端生效，不参与合成。
- **音高**：根本不发给 API（OpenAI 兼容接口没有 pitch 字段）。

语速有个坑：`rate < 1` 时服务端不接受，代码改用播放端 `playbackRate` 拉伸时间轴，此时服务端仍按 1 合成。所以键里存的是**真正发给服务端的语速**（`speedHandledByServer ? rate : 1`），否则 0.8 和 0.9 会被存成两份一模一样的音频。

## 3. 存储与容量

- 表：`ttsCache`，DB v9 新增，索引 `key, lastUsedAt, bytes`。
- 存的是合成结果的 base64 与 contentType，命中后走与网络返回完全相同的播放路径，不额外分支。
- 容量：**60 条** 且 **30 MB** 双上限，超了按 `lastUsedAt` 从旧到新删。
  - 30MB 的口径是 base64 字符数（IndexedDB 按 UTF-8 单字节存），换算成实际音频约 22MB，单声道 MP3 约能放一小时语音。
- 命中时刷新 `lastUsedAt` 与 `hits`（异步回写，失败不影响播放）。

`bytes` 记的是 base64 长度而非解码后的体积，偏大约 33% —— 这是故意保守：宁可少存一点，也不要估小了把手机撑爆。

## 4. 边界

- **只缓存 API 引擎**。原生 TTS（`speechSynthesis` / Android 桥）不出字节，没有可缓存的东西，也不消耗额度。
- **错误不缓存**：只有 `ok && base64` 才写库。
- **缓存读写失败一律降级为未命中**，不能因为缓存问题导致读不出声。
- **不参与备份**：`exportFullBackupJson` 显式列举要导出的表，`ttsCache` 不在其中，备份体积不受影响；导入也不会动它。
- 设置页显示「语音缓存 N 条 · X MB」并提供「清空」。

## 5. 换音色 / 编辑消息的自动失效

不是额外机制，而是键完整性的副产品：

- 换音色 / 模型 / 语气 / 服务端语速 → 键变 → 未命中 → 重新合成。
- 编辑消息 → 文本变 → 键变 → 重新合成。

旧条目不会立即消失，留在库里等 LRU 淘汰。它们永远不会被命中，只占空间，属于可接受成本（换来的是删除路径极简，不需要按消息 ID 反向清理）。

## 6. 没做的事

- 不做跨端同步的音频缓存（内容寻址的键是现成的，但需要云端存储，超出本地优先的定位）。
- 不做按会话维度的批量预热。
- 不做缓存命中率的 UI 统计（`hits` 字段已记，需要时再展示）。

## 7. 换音色后沿用旧语音（可选，默认关）

换音色意味着换文案缓存键，旧额度就白花了。但「沿用旧音频」会让用户听到旧音色，两难，所以交给用户开关：`ttsCacheKeepOldVoice`。

实现上不需要第二套缓存，只是多存一个**音色无关键** `agnosticKey`（文本 + 模型 + 服务端语速 + 增益 + 语气，去掉音色）：

- 全键命中 → 用新音色的音频（正常路径）
- 全键未命中且开关打开 → 用 `agnosticKey` 找最近一条旧音频兜底，不请求接口
- 开关关闭 → 直接重新合成

代价是可能播出旧音色，所以默认关闭，文案也写明了这一点。

## 8. 按对话选择性清理

缓存条目带上 `sessionId`（朗读时由消息所属会话传入），设置页可按会话聚合展示「这场对话占了多少」并单场删除，避免只能"全清"。

`sessionId` 为空的旧条目归到「未归属对话（较早的朗读）」，同样可单独清理。

注意：删除后再次朗读会重新请求合成、消耗额度，UI 里已提示。
